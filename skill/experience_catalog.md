# PenumbraSight 技能包

本目录是把开发过程中与大模型协作沉淀下来的可复用经验**显式提炼**出来的结果，供他人直接复用到其他题目上。

赛方定义的可复用性标准是：**一支陌生队伍拿到该目录，能否直接用在自己的题目上**。因此每一项都必须写明「适用场景、使用方法、已验证效果、失效条件」，并说明是从哪些失败或观察中总结得出。

## 1. 条目规范

每个条目须包含以下五段，缺一不可：

| 字段 | 要求 |

| 适用场景 | 换一个题目、换一块板卡之后，这个条目仍然适用的条件 |

## SK-001 竞赛提交形态合规自检清单

**类型**：案例模板 + 踩坑清单

**适用场景**：任何「以代码仓库 + 设计报告」为提交形态的竞赛或项目验收，只要主办方给出了明确的提交内容清单与推荐目录结构。与具体器件、题目无关。

**使用方法**：

1. 把主办方给出的「提交内容」逐条抄成一张表，每条给一列「当前是否有对应产出」。
2. 对每一列填三种状态之一：`已覆盖` / `需成章` / `完全空白`。
3. 特别注意主办方的**评测权重表**：把权重乘到覆盖度上，算出加权覆盖分。这一步的作用是让「哪里最值得立刻投入」变成算术题，而不是靠感觉。
4. 优先处理「完全空白且权重高」的项——这类项通常不需要技术研发，只需要纪律。
5. 对「推荐目录结构」，若实际结构不同，必须在 README 中给出目录对照说明，不能只靠评委猜。

**已验证效果**：在 PenumbraSight 项目上，用该方法发现「大模型协作记录 + 技能包」一项在权重表上占 15 分，而现有方案文档完全空白；同时发现三处提交形态问题（目录结构、开源协议、验证结果未成章）。该方法把 46 分的交付形态缺口从「隐性风险」变成了「可勾选的清单」。

**失效条件**：主办方没有公开提交内容清单或评测权重时，本清单退化为通用检查表，价值大幅下降。此外，若项目尚未产出任何技术内容，本清单会给出「大面积空白」的结论而没有可操作性。

**来源**：在一次参赛方案分析中，逐条比对官方选题指南的「提交内容」与「评测指标与权重」两节，与实际技术方案文档交叉核对后发现系统性缺口。教训是：技术方案写得再细，也可能整段缺失赛方要求的交付物类别。

## SK-002 无硬件环境下的算法开发可执行性盘点

**类型**：校验清单 + 提示词工作流

**适用场景**：硬件（开发板、相机、传感器）尚未到货，但需要立刻推进算法开发时。用于判断「哪些任务现在就能做、哪些必须等」。

**使用方法**：

1. 先用一条命令列出全部相关工具链的存在性，而不是凭印象判断。要查的是：语言运行时、包管理器、C/C++ 编译器、EDA 工具、仿真器、版本控制、磁盘可用空间。
2. 关键判据不是「工具在不在」，而是**数据能不能读**。先探测数据文件的实际格式，再判断是否需要额外依赖。
3. 把任务按可执行性分三档：本机立即可做 / 需先装工具 / 必须到其他机器做。
4. 对每一档分别给出「谁能做、需要什么前置」。
5. **不要擅自安装外部软件**：把安装需求单独列出来交给使用者决策。

**已验证效果**：在 PenumbraSight 项目上执行本清单，得到两个决定性结论——(a) 官方 `.mat` 是 MATLAB 5.0 格式，`scipy.io.loadmat` 可直接读取，**不需要 h5py**；(b) 主机上存在 g++，因此 HLS 的 C++ 源码可以**在没有 Vitis 的情况下先做主机侧等价仿真**，把算法正确性提前钉死。这两条把原本被认为「必须等硬件」的工作提前了。

**失效条件**：数据文件的格式若未公开、或依赖专有 SDK 才能解析，则第 2 步会失效，此时需要先解决数据读取问题。另外，本清单只能判断「能不能跑」，不能判断「跑得对不对」。

**来源**：源自一次「板卡未到但需要开工」的排期困境。最初的排期把若干任务列为「依赖硬件」，盘点后发现其中多数只依赖工具链而不依赖硬件。教训是：**把「依赖硬件」与「依赖工具」混为一谈，会凭空制造等待时间。**

## SK-003 MATLAB 遗产代码到 FPGA 的移植边界判定

**类型**：提示词工作流

**适用场景**：手上有参考实现的 MATLAB（或 Python/NumPy）研究代码，需要判断哪些部分应该移植到 FPGA、哪些应该留在主机、哪些应该换算法。

**使用方法**：

按以下四问逐个函数判断，不要整体判断：

1. **它是否只运行一次就产出可复用的产物？** 若是（如几何建模、矩阵分解），留在主机离线，把产物（量化后的因子）下发。
2. **它的复杂度是否随候选/搜索空间线性膨胀？** 若是（如对大量候选位置逐个求逆或分解），这是最该进硬件的一类，但要先做数学变换以减少在线计算量。
3. **它是否含数据依赖的动态控制流？**（回溯线搜索、变长迭代、动态网格细化）若有，必须换成固定迭代次数的算法才能在硬件上得到确定延迟。
4. **它是否是逐样本、无反馈的流水操作？** 若是，直接写 RTL 最自然。

判定完成后，把结论整理成一张「函数 → 归属（PC 离线 / PL-RTL / PL-HLS / PS）」的表，这张表同时就是设计报告里「软硬件划分依据」一节的现成内容。

**给大模型的提示词模板**：

> 以下是一份研究代码的函数清单与各自的功能描述。请对每个函数回答四个问题：(1) 是否只运行一次并产出可复用产物？(2) 复杂度是否随搜索空间膨胀？(3) 是否含数据依赖的动态控制流？(4) 是否为逐样本无反馈流水？然后给出每个函数的归属建议（主机离线 / RTL / HLS / PS 软件），并明确指出哪些函数需要**更换算法**而不是移植。不要假设所有函数都需要移植。

**已验证效果**：在 PenumbraSight 项目上对官方仓库 `Functions/` 下的 14 个函数套用本方法，结论是**只有三个数学算子加一条流式链路需要进硬件**，占大头的几何建模与矩阵分解应留在 PC 离线。按原字面理解「把 MATLAB 移植到 Verilog」，会把 SVD 与大规模矩阵生成也列入移植范围。

**失效条件**：若参考实现本身已经是面向硬件的（如已经是 HLS C++），本方法会给出「全部移植」的正确但无用的结论。另外，本方法只判断**归属**，不判断**可行性**——某个函数归属为「HLS」不代表在目标器件的资源下一定收敛。

**来源**：源于一次任务澄清。需求原话是「把 MATLAB 代码移植到 Verilog 上并仿真」，而逐函数分析后发现这句话若按字面执行会导致工期不可控。教训是：**对研究代码的移植需求，第一件事是划定边界，而不是开始翻译。**

## SK-004 公开研究数据集的契约提取法

**类型**：校验脚本 + 踩坑清单

**适用场景**：拿到一份第三方或公开研究数据集，准备为算法移植与定点硬件设计建立输入契约时。与数据类型无关，只要数据以结构化文件（`.mat`、`.h5`、`.npz`）成组发布即适用。

**使用方法**：

1. **逐文件**（而不是逐数据集）提取：形状、dtype、是否全为整数值、min / max / p99.9、以及任何随文件携带的元数据字段。批量产物写成一张 CSV 而不是几个汇总数字。
2. **不要把论文里的位深当成数据的位深**。论文写「14-bit 相机」指的是采集器件，发布数据可能被重新量化到 16 bit 容器甚至 float64。
3. **不要用 `max / 满量程` 反推累积倍数**，除非确认画面中确实存在饱和像素；否则会得到一堆无意义的非整数倍数。
4. **专门找「配置文件」类文件**。研究代码常把中间状态存盘（网格定义、中间分数、真值、几何参数），这类文件里往往有验证算法所需的全部参照量。
5. **对每个后续模块分别声明它需要原始数据还是官方预处理产物**。两者通常分辨率不同、量纲不同，不能混用；若必须用预处理产物，就要评估能否从原始数据重新生成目标格式。
6. 把结论写成一份 `data_contract.md`，明确列出「实测值」与「推断值」，并单列一节「残留待确认项」。

**已验证效果**：在 PenumbraSight 项目上对一个 136 文件 / 1.4 GB 的研究数据集执行本方法，得到三条改变计划的结论：

- 数据量纲跨约 3 个数量级（单文件 p99.9 从 1 万到 520 万），**推翻了「按统一 16-bit 满量程设计定点流水」的原计划**，并发现原 20-bit 块和预算可能需上调至 23 bit；
- 官方预处理产物是 126×126，而本方案的流水线契约是 96×96，**接口对不上**；但原始 2016×2016 图全部保留，可从原始图重新分块解决；
- 官方把「测量 → 搜索网格 → 各轮投影分数 → 位置估计 → 真值」全部存成了 .mat 文件，因此**在完全没有原工具链（MATLAB）的情况下也能验证算法正确性**——这一条把原本被判定为「阻塞主线」的缺口变成了非阻塞。

**失效条件**：若数据集只发布预处理后的产物而无原始数据，第 5 步无从执行，只能调整自身流水线去适配；若研究代码不保存中间状态，则仍需要原工具链做对照。此外，本方法只建立**输入契约**，不判断数据本身的质量或标注准确性。

**来源**：起因是发现主机上只有 MATLAB Runtime 而没有 MATLAB，一度判断「无法与官方结果对齐，主线受阻」。改为先逐文件盘点数据后，发现官方把中间状态一起存了盘。教训是：**在宣布「缺少某个工具所以无法验证」之前，先把数据本身翻一遍——研究者经常把验证所需的中间量顺手存了下来。**

## SK-005 用参考实现的中间结果做 bit-exact 黄金对照

**类型**：校验脚本 + 提示词工作流

**适用场景**：手上有一个参考实现（研究代码、开源项目、论文附带脚本），但**缺少运行它的环境**（许可证、依赖、平台不匹配），需要证明自己的重实现是正确的。适用于任何"照论文/开源实现重写"的场合。

**使用方法**：

1. **先翻参考项目的输出目录找"存档"类文件。** 研究代码常把中间结果、真值、每轮参数一并存盘，这类文件里往往包含验证所需的全部参照量。
2. 从存档文件中**反推完整参数**：本例需要的是每通道平面尺寸、墙上采样点数、分块尺寸、Bayer 相位。这些参数若靠猜，重实现几乎不可能吻合。
3. 用这些参数独立实现，然后**逐元素比对，而不是只比统计量**。统计量吻合可能只是巧合。
4. 判据是逐元素相等（`max|diff| = 0`）。若做不到，继续排查直到逐元素吻合，或明确指出差异根因（如浮点求和顺序）。**不要用"统计上接近"结案。**
5. 把黄金对照脚本纳入仓库作为长期回归测试。它同时是"功能正确性是如何确认的"这一赛方要求的直接证据。

**已验证效果**：在 PenumbraSight 项目上，用独立实现的 Bayer 解交织 + 8×8 分块平均，从原始 RAW 图精确复现了官方测量 `meas_r/g/b`，`max|diff| = 0`；同时验证了帧累积为**求和而非平均**。这一步把"没有 MATLAB 所以无法验证"变成"已验证 bit-exact"，并把 MATLAB 从关键路径上移除。

**失效条件**：若参考项目只发布最终结果而没有中间产物、或原始输入不公开，则无法建立黄金对照，只能退化为统计相似性检查，证据强度大幅下降。

**来源**：原以为缺少 MATLAB 会阻塞主线，改为先逐文件盘点数据后发现官方把中间状态一起存了盘。教训是：**「缺少参考环境」往往只是「没找到参考产物」——先把参考项目的输出目录翻一遍，再决定是否真的需要那个环境。**

## SK-006 弱信号测量链的信噪比与帧预算建模

**类型**：校验脚本

**适用场景**：成像、传感或测量类项目，信号远弱于噪声，需要定量回答「要累积多少帧、多长时间才够」。与具体物理量无关，只要同一场景有多次重复采集即适用。

**使用方法**：

1. 在重复采集的数据上（本例为 35 帧序列），**逐帧独立**算出目标量（本例为差分测量）。
2. 把单帧量写为 `d_i = s + n_i`：用帧均值估计信号 `s`，用**逐像素时间标准差**估计噪声 `sigma`。
3. 计算**单帧信噪比 `std(s)/sigma`**。若小于 1，说明单帧根本不可用，必须累积——这是一条应当在方案设计早期就确立的事实。
4. 由 `SNR(N) = sqrt(N) * std(s) / sigma` 反解达到目标 SNR 所需的帧数。
5. 用「与满帧累积的相关系数」作为独立佐证：它应随 N 单调上升并趋近 1；若不然，说明噪声不独立或存在漂移。
6. 出两张图：**同尺度色标的 N 递增图像对比**（直观展示"多少帧才能看见"），以及 SNR–N 曲线（定量，标注目标 SNR 的交叉点）。

**已验证效果**：在 PenumbraSight 项目上测得单帧差分信噪比 **0.672**，达到 SNR ≥ 3 需约 **20 帧**。官方数据集各场景记录的累积帧数为 10 / 35 / 40 / 50，与模型给出的量级一致，构成独立交叉验证。该结论直接推翻了原方案的「1 / 4 / 8 帧」档位设定，并推导出一条设计约束：**快速告警通路必须改用积分型统计量**（如低维子空间投影能量），因为逐像素判据在单帧时会被噪声完全淹没。

**失效条件**：要求同一场景有多次重复采集。若只有单次采集，只能做空间噪声估计，而空间估计会混入信号自身的高频成分、无法分离，可靠性低得多。另外本模型假设噪声帧间独立；若存在固定图形噪声（FPN）或缓慢漂移，实际累积增益会低于 sqrt(N)，需用暗场帧单独验证。

**来源**：源于需要验证项目最大的技术风险「光学信噪比够不够」。最初用空间高频量作噪声代理，发现该指标会随信号一起增长、无法分离噪声；改用帧间时间标准差后才得到可辩护的结果。教训是：**估计噪声要利用「重复」这个自由度；只靠单帧的空间统计，无法把噪声与信号的高频成分分开。**

## SK-007 用「实际达成量」反推官方设计目标

**类型**：提示词工作流 + 校验脚本

**适用场景**：使用公开数据集或参考实现时，需要推断原作者在多项参数上遵循的设计准则。典型情形是每份样本的参数组合各不相同，表面看不出规律，但背后存在一个统一的目标量。

**使用方法**：

1. 把每份样本的**同一物理量**用同一个模型算出来，而不是只看原始参数。本例中参数是「累积帧数」（9~35 不等），算出的量是「单帧信噪比 × √帧数」。
2. 逐样本算完后再看分布。若各样本的**达成值高度一致**，说明原作者是按这个目标量定参的。
3. 一致性用离散度量化（(max−min)/mean），不要只说「差不多」。本例为 13%。
4. 得到的目标值可直接作为自己的设计指标，比自己拍一个阈值更可靠。
5. 若达成值离散度很大，说明该目标量不成立，回到第 1 步换一个候选量再试。

**已验证效果**：在 PenumbraSight 上，官方五个场景的累积帧数为 9/12/13/35/35，看似无规律；换算成「实际达成信噪比」后为 4.52/3.98/3.45/3.68/3.92，**均值 3.91、离散度仅 13%**。由此确认官方是按「达到约 4 的目标信噪比」逐场景定帧数的。该结论直接推翻了原方案「固定 8/16/32 三档」的设计，改为「在线估计单帧信噪比后按目标值反解帧数」。

**失效条件**：要求样本间除目标参数外条件可比（同一相机、同一分析方法）。若不同样本用了不同相机或不同场景几何，达成值会被系统性偏差污染，一致性检验失去意义。

**来源**：原方案打算按场景难度拍脑袋定三档累积。改为先算达成值后才发现规律。教训是：**当多个样本的参数看不出规律时，通常不是没有规律，而是看错了量——试着把参数换成一个可计算的物理量再看分布。**

## SK-008 大矩阵 SVD 降维为小矩阵特征分解

**类型**：校验脚本（性能优化）

**适用场景**：需要对大量候选矩阵反复计算「向量投影到截断值域的能量」这类量，而矩阵的行数远大于列数（本例 15876 × 1044）。直接对每个候选做 SVD 在脚本语言里不可行。

**使用方法**：

1. 需要的是投影能量 `||U_K U_K^T y||²`，**不是** U 本身。写出 `U_K U_K^T = A V_K S_K^{-2} V_K^T A^T`，其中 V、S 来自 `A^T A` 的特征分解。
2. 于是能量化为 `sum_{k in K} (v_k^T A^T y)² / s_k²`，只需一次 `A^T y`、一次 `A^T A` 和一次 N×N 特征分解。
3. 规模从 M×N 的 SVD 降到 N×N 的特征分解。本例 N=1044 而 M=15876，单次候选耗时从不可行降到约 0.7 秒。
4. 同一份特征分解可复用于多个截断阈值：多算几组 `keep` 掩码即可，不必重算分解。

**已验证效果**：PenumbraSight 的遮挡物位置搜索需要在 972 个候选位置上评估投影能量。采用该技巧后整轮搜索可在十余分钟内跑完；未采用时单次候选就无法在合理时间内完成。

**失效条件**：当 N > M 时该变换反而更慢（`A^T A` 变成 M×M 但秩不足），此时应改用对 A 本身的截断 SVD 或随机化 SVD。另外 `A^T A` 的条件数是 A 的平方，若 A 本身病态，需先做列归一化或加正则。

**来源**：来自 T0-04 实现定位评分时遇到的性能瓶颈。教训是：**先想清楚到底需不需要那个中间结果（这里是左奇异向量）；把它从公式里消掉，往往能把规模降一个维度。**

## SK-009 定点位宽须按数据容器位宽预算，而非传感器标称位宽

**类型**：踩坑清单

**适用场景**：为流水线设计定点格式时估算位宽增长。常见误区是直接采用器件手册上的传感器位深。

**使用方法**：

1. 不要用传感器标称位深做预算。**先实测数据的实际数值范围与容器位深**（读若干样本的 dtype 与 min/max）。
2. 按容器位宽加上累加级数的增长：块累加需 `容器位宽 + ceil(log2(块内像素数))`；帧累积再需 `+ ceil(log2(帧数))`。
3. 把三级增长（块累加、帧累积、矩阵累加）分别列出，取最大值作为下游位宽，不要只算一级。
4. 用满量程数据做一次饱和测试：全满输入经各级累加后的结果应等于理论最大值，据此核对位宽。
5. 若数据经过第三方重新量化（很常见），以重新量化后的容器为准。

**已验证效果**：PenumbraSight 的论文写「14-bit 相机」，原技术方案据此按 12-bit 源设计块和为 20 bit。实测官方数据被重新量化到 **16-bit 容器**（满量程 65535），因此 10×10 块和实际需要 **23 bit**，原设计会溢出 3 bit。该问题在预处理阶段就被单元测试锁定（`test_fixed_point_bit_budget`）。

**失效条件**：若上游已做过归一化或浮点转换，容器位宽不再是位宽的约束来源，此时应改为按数据的实际动态范围（有效位数）预算。

**来源**：来自 T0-01 数据契约提取时发现官方数据满量程为 65535 而非 4095。教训是：**器件手册给的是物理量程，数据文件里装的是容器位数，两者常常不一致；预算位宽时以后者为准。**

## SK-010 批量候选任务的并行度配置（进程数 × BLAS 线程数）

**类型**：踩坑清单

**适用场景**：需要对大量**相互独立**的候选或样本反复做中等规模的矩阵运算（本例每次约 0.3 到 1 秒），希望缩短总耗时。与具体算法无关，只要单个任务是「中等规模 NumPy 运算」即适用。

**使用方法**：

1. 先单进程跑 3 到 5 个样本，得到单样本耗时。这是基准。
2. 再直接开「物理核数」个进程跑 20 个样本，测实际吞吐。**不要假设加速比等于进程数**。
3. 若发现多进程比单进程更慢，原因几乎一定是 **BLAS 自身的多线程与多进程在争抢**——每个进程都想占满所有核。
4. 解决方法：在**导入 numpy 之前**把下面几个环境变量设为 `1`，再按物理核数开进程：

   ```python
   import os
   os.environ.setdefault("OMP_NUM_THREADS", "1")
   os.environ.setdefault("MKL_NUM_THREADS", "1")
   os.environ.setdefault("OPENBLAS_NUM_THREADS", "1")
   import numpy as np   # 必须在这之后
   ```

   **导入 numpy 之后再设无效**，这一点是关键，容易踩。
5. 目标是让「进程数 × 每进程线程数 ≈ 物理核数」。

**已验证效果**：在 PenumbraSight 上计算 972 个候选的评分场（每个候选含一次 M×N 矩阵构造、一次 Gram 矩阵、一次 N×N 特征分解，N=1044、M=15876）：

| 配置 | 总耗时 |
|---|---|
| 单进程，BLAS 多线程 | 1060 s |
| 8 进程，BLAS 多线程 | **1346 s（反而更慢）** |
| **10 进程，BLAS 单线程** | **297 s（快 5.9 倍）** |

**失效条件**：若单样本是访存密集型而非计算密集型，限制线程数可能无收益；若单样本内部并行度已经很高（或样本本身很大），多进程会因内存带宽饱和而失效。另外本条目只优化**吞吐**，不优化单次延迟。

**来源**：来自 C0 任务的第一次运行——加了 8 进程后，脚本自己预估的总耗时从 18 分钟涨到 22 分钟，与「进程越多越快」的直觉相反。教训是：**并行之前先测一次实际吞吐，不要用进程数当加速比。**

## SK-011 差分（去背景）与低秩近似互斥

**类型**：踩坑清单

**适用场景**：信号或图像处理中，先用「低秩 / 低阶多项式」近似表示某个算子（几何权重、照明场、背景场），再对它做**差分、去均值或去背景**，然后计算二阶量（Gram 矩阵、协方差、能量）。这类结构在计算成像、阵列信号处理、光传输建模中很常见。

**使用方法**：

1. 先判断这个低秩近似作用在什么成分上。若它作用在**低频、平滑**成分（`1/r⁴` 型权重、平滑照明场），而下游操作是**差分**（去背景、提取边缘），就已经处在风险区。
2. **不要展开差分**。把差分写成「四项大数相减」的形式，会让抵消暴露出来。
3. 定量检查，判据很明确：设近似相对误差为 `eps`，差分展开各项的量级为 `S`、最终结果为 `R`。若 `eps × S > R`，则该路径**在数值上必然失败**，与实现无关。
4. 三条出路：保留精确算子做差分（接受计算量）；把近似作用在差分后的量上（若仍可分解）；或提高近似阶数直到第 3 步的判据不成立。

**已验证效果**：PenumbraSight 的定位评分需要在 972 个候选上算 `A_d^T A_d`（`A_d` 是 `A` 的行差分）。用秩 3 近似 `1/‖v‖⁴`（相对误差 **0.1535%**）配合「前缀和 + 矩形包含排除」：

| 对象 | 快速路径的误差 | 结论 |
|---|---|---|
| 未差分的 `A^T A` | **0.0264%**（比近似自身的误差还小 6 倍） | 成立 |
| 差分后的 `A_d^T A_d` | **181.85%** | **不成立** |

原因：差分展开的四项各自量级 **4.3e6**，而组合结果只有 **5.9e3**（损失约 4 位有效数字）；近似误差作用在大数上产生约 **6500** 的绝对误差，**比结果本身还大**。

**根因**：低秩近似保留的是平滑低频，而差分去掉的恰是平滑低频、保留半影高频——**两者的需求正好相反**。

**失效条件**：若被差分的信号本身没有强背景（差分前后量级相近），则不存在抵消，本条目不适用。

**来源**：来自 A6 任务验证「`A^T A` 是否有快速算法」时的一个案例——**数学推导完全正确，数值上彻底失败**。它同时解释了同一项目里另一条独立发现的约束（「不得先把定点化的 A 相减得到 A_d」）：两者是同一种灾难性抵消的不同表现。教训是：**推导正确不等于可算；涉及「大数相减」的结构，必须在做优化之前先做量级检查。**

## SK-012 用高优化等级编译当作正确性检查

**类型**：踩坑清单

**适用场景**：把参考实现（Python / MATLAB）改写成 C / C++ 并做主机侧验证时。尤其是数组、指针、循环边界较多的定点或图像处理代码。

**使用方法**：

1. **不要只用 `-O0` 验证正确性。** 加 `-O2`（或 `-O3`）并同时开 `-Wall -Wextra`。
2. 特别留意 GCC 的 `-Waggressive-loop-optimizations`：它在 `-O2` 以上会检测出「循环索引必然越界」，并明确告诉你这是**未定义行为**。这条警告在 `-O0` 下不会出现。
3. 把警告当错误处理：验证阶段加 `-Werror`，或至少逐条看完。**「编译过了」不等于「写对了」。**
4. 真正的完备检查仍应配合 `-fsanitize=address,undefined`，但高优化等级能在最省事的前提下先抓出一批问题。

**已验证效果**：在 PenumbraSight 的预处理链主机测试中，一个数组声明为 100 个元素、却被按 10000 个元素的索引访问（`tmp[NBLK]` 应为 `tmp[PH*PW]`）。GCC 在 `-O2` 下直接报 `iteration 1 invokes undefined behavior [-Waggressive-loop-optimizations]`。

这个 bug 的危险之处在于**它在 `-O0` 下不会报警，而且很可能「碰巧跑对」**——越界的写入落在相邻栈内存上，若那块内存恰好没被后续使用，测试结果就会全部通过。也就是说，**低优化等级会给出虚假的成功**。

**失效条件**：警告能力依赖编译器的静态分析，不完备；不同编译器（gcc / clang / MSVC）报警范围差异很大。跨平台代码不能只信任单一编译器的警告。另外，高优化等级会改变浮点运算的合并顺序，做浮点位级比对时反而应锁定 `-O0` 或显式关闭 fast-math。

**来源**：来自 L1-1 把预处理链改写成 HLS 风格 C++ 时的实际编译警告。教训是：**编译器在高优化等级下的警告，本身就是一层免费的静态检查；把优化等级降下来调试，会同时关掉这层检查。**

## SK-013 否定性结论前必须先找成功参照

**类型**：检查清单

**适用场景**：当你准备得出「数据信息量不足」「这个问题做不到」「上限只有 X」这类**否定性结论**时，尤其是要据此砍掉一个功能模块之前。

**使用方法**：

1. **在写下否定结论之前，先问一句：有没有已发表的、公开的实现，用同样的数据做成过？** 有的话，先把它跑通或读通，再回头审视自己的结论。
2. **检查自己的「理论上限」是相对什么算的。** 上限往往依赖于一个中间产物（矩阵、模型、标定参数），而这个中间产物可能本身有错。**中间产物错了，上限就错了，而结论会被误认为是「数据的性质」而非「实现的性质」。**
3. **明确标注上限的适用范围**。写「在当前实现 A 下的上限」，而不是「该问题的上限」。前者可被修正，后者会误导决策。
4. **对「三条独立证据」保持警惕。** 如果多条证据共用一个未验证的前提，它们**不是独立的**——只是同一个前提的三种表现。正确做法是先独立验证那个前提。

**已验证效果**：在 PenumbraSight 项目中，我基于「线性上限 7.29 dB ≈ 均值预测 7.24 dB」「条件数 8506」「测量与 A 被同一低维结构主导」三条证据，判定隐藏场景重建「受数据信息量限制、无法完成」，并据此建议把重建整个模块从作品里砍掉。后来队友跑通论文官方实现，**用同一份数据重建出了清晰可辨认的图像**——三条证据共有的隐含前提「我的 A 矩阵正确」是错的，那三条其实是同一错误的三种表现。

**代价**：这次误判差点让作品砍掉核心模块。若按原判断执行，损失无法挽回。

**失效条件**：这条清单适用于「因实现原因而失败」的场合。若参照实现用了不同数据、不同先验或不同评价标准，对照就不成立，需要先确认可比性。

**来源**：来自 S0-4 结论被论文官方实现推翻的实例，见 `01_分析报告/06_阶段零产出/S0-4_结论更正.md`。这是本项目第四次自我纠正。

## SK-014 残差数值不能作为差分方向/几何正确性的判据

**类型**：踩坑清单

**适用场景**：在几个候选模型（不同的差分方向、不同的几何参数、不同的行序约定）之间挑选「哪一个是对的」时，如果你打算用「拟合残差更小」来选，先看这一条。

**使用方法**：

1. **把残差当成「排除法」而不是「选择法」。** 残差能可靠地告诉你「某个模型完全不对」（残差接近 1），但不能告诉你「哪个更对」。
2. **在病态问题里，残差小的那个模型往往是把信息量大的分量丢掉的那个。** 丢掉难拟合的分量，剩下的自然好拟合。这是严重的自欺。
3. **最终判据必须是「能否恢复已知真值」。** 拿一个已知答案的数据集跑完整重建，看结果对不对——这比任何残差指标都可靠。
4. 若确实需要标量指标，用**与真值的相关系数**，而不是模型的拟合残差。

**已验证效果**：PenumbraSight 重建任务中，两个候选差分方向（水平 / 垂直）的差分最小二乘残差分别是 0.173 和 0.515，差 3 倍。我据此选了「水平」——结果重建出的是**竖条纹**（因为水平差分几乎不约束隐藏场景的纵向维度，TV 项把该维度压成常数，这不是真解而是病态+正则化的假象）。「垂直」方向虽然残差数值大，却能真正恢复出 BU 图案（r=+0.373，肉眼可辨）。**残差与正确性在这里完全反向。**

**失效条件**：当问题是良态的、模型类相同、且数据噪声已知时，残差（或 AIC/BIC 之类）是有效的模型选择依据。本条针对**病态反问题 + 不同模型结构**的比较。

**来源**：来自 Y0 前向模型交叉验证，见 `01_分析报告/11_算法移植重规划/Y0_前向模型与求解器诊断记录.md`。

## SK-015 选迭代求解器前先量条件数

**类型**：检查清单

**适用场景**：为一个线性/近线性反问题挑选迭代求解器时；或者发现「算法公式明明对，但结果就是不对」时。

**使用方法**：

1. **先算条件数。** 对最小二乘问题算 `ATA` 的 `λmax/λmin`（`np.linalg.eigvalsh` 即可，规模小的时候秒级）。
2. **条件数超过 1e4 时，固定步长的一阶方法基本不可用。** PDHG、ISTA、固定步长梯度下降都需要 O(条件数) 量级的迭代次数才能收敛到有意义的精度。
3. **换用带线搜索的方法**（回溯线搜索允许在平坦方向取大步长），或**引入二阶信息**（CG / LSQR 内迭代 + 分裂类方法）。
4. **先测「问题本身能解到多好」再测「求解器差多少」**：用精确解（`np.linalg.solve`）和 CG 在**无噪声合成数据**上跑基线，再对比迭代法的结果。二者的差距就是求解器的锅。

**已验证效果**：PenumbraSight 的差分重建问题，`ATA` 条件数 6.4e5。无噪声合成数据上：精确 LS 的 r=1.000000、CG(200 次) 的 r=0.999992，而固定步长 PDHG 迭代 500/2000/8000 次分别只有 0.617/0.731/0.843——**迭代 8000 次仍在爬坡**。换成论文的带线搜索 FISTA 后，同样的 1100 次迭代即可得到可用结果。

**失效条件**：问题规模很小、或只需要低精度解、或矩阵有良好的预处理时，固定步长方法仍然可用。另外，定点硬件实现时线搜索本身很贵，需要权衡（可考虑把线搜索次数固定为常数）。

**来源**：来自 Y0 求解器诊断，`convergence_test.py` 与 `paper_fista.py`。

## SK-016 移植前先做「合成数据自洽性测试」

**类型**：检查清单

**适用场景**：把一套算法从参考实现（MATLAB/Python）移植到另一种语言或硬件（HLS/FPGA/C++）之前；或者移植后结果不对、但分不清「是模型抄错了」还是「算法本身在这个数据上做不到」时。

**使用方法**：

1. **用你自己实现的模型 A 造一份无噪声的合成测量**：`y = A @ x_true`。
2. **用你自己实现的重建管线去恢复 `x_true`。** 做两步：
   - 精确最小二乘（`np.linalg.solve`）—— 应能 100% 复原；
   - 你实际要用的迭代求解器 —— 应能逼近那个精确解。
3. **判读**：
   - 精确 LS 复原不了 → 差分/展平序/列置换等**框架性错误**；
   - 精确 LS 能复原、迭代法不能 → **求解器选型或收敛问题**；
   - 两者都能复原、真实数据不能 → **模型与真实数据的偏差**（几何、标定、朝向）。
4. 这一步能把三类问题**彻底分开**，避免在三者之间反复猜。做完再去看真实数据。

**已验证效果**：PenumbraSight 项目里，真实数据重建出的图像明显不对（竖条纹）。我先后试过 8 种二面体变换、±40 像素平移搜索、4 种行序/翻转组合，全是猜。做了合成数据自洽性测试后，**一次就分清了**：精确 LS 复原到 r=1.000000 → 框架没错；迭代法只到 0.617 → 求解器欠收敛；真实数据只到 0.373 → 剩下的才是模型偏差。**没有这一步，前面所有试探都无法收敛到结论。**

**失效条件**：模型本身是随机的、或含有不可微/非凸成分时，合成数据自洽性测试的结论要谨慎解读。另外，若真实数据的噪声结构对算法影响很大（例如病态放大），合成无噪声测试通过并不能保证真实数据可用——它只保证「实现没错」。

**来源**：来自 Y0 诊断，`synth_test.py` 与 `convergence_test.py`。
